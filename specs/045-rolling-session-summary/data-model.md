# Data Model: Rolling Session Summary

**Feature**: 045-rolling-session-summary  
**Date**: 2026-04-13

## Overview

This feature introduces no persistent data model changes. All data is transient — computed per-request and discarded after the response is sent.

## Entities

### Conversation Turn (existing, unchanged)

A question-answer pair sent by the frontend as part of the request payload.

| Field    | Type   | Description                    |
|----------|--------|--------------------------------|
| question | string | The user's question text       |
| answer   | string | The assistant's response text  |

**Source**: Frontend `_history` list → sent as JSON array in `/manuals/ask` request body.

### Session Summary (new, round-tripped via frontend)

A compressed text representation of older conversation turns, generated by the backend and cached by the frontend in ChatTab state.

| Field            | Type            | Description                                                        |
|------------------|-----------------|--------------------------------------------------------------------|
| session_summary  | string (nullable) | 3-4 sentence summary of compressed turns, preserving technical facts |

**Lifecycle**:
1. Created: During `ask()` processing when `len(history) > 8` and no existing summary covers those turns
2. Returned: Backend includes `session_summary` in the response JSON
3. Stored: Frontend saves it in ChatTab state (`_sessionSummary` field)
4. Sent back: Frontend includes `session_summary` as an optional field in subsequent requests
5. Reused or re-compressed: Backend reuses the summary if it still covers all old turns, or re-compresses (existing summary + newly aged-out turns) when new turns push past the 4-turn raw window

**Not persisted to database**: Lives in frontend in-memory state for the session duration. Lost on page refresh (acceptable — history is also lost on refresh).

## State Transitions

```
Request received (N turns + optional session_summary)
    │
    ├── N <= 8: No compression → all turns sent as raw history
    │            Response: {answer, session_summary: null}
    │
    └── N > 8:
         │
         ├── session_summary provided & covers turns[0..N-4]:
         │     Reuse summary as-is → summary + turns[N-4..N] as raw history
         │
         └── session_summary missing OR new turns aged out:
               Re-compress (existing summary + newly aged-out turns) → updated summary
               → summary + turns[N-4..N] as raw history
               → On compression failure: fallback to turns[N-10..N] as raw history
               
    Response always includes: {answer, session_summary}
```

## Schema Changes

None. No database migrations required.
