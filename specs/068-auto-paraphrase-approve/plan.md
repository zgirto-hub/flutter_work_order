# Implementation Plan: Auto-Paraphrase on Admin Approve

**Branch**: `068-auto-paraphrase-approve` | **Date**: 2026-04-16 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `specs/068-auto-paraphrase-approve/spec.md`

## Summary

When an admin approves a pending answer in the Ask-the-AI admin screen, generate 3–5 paraphrased variants of the source question via the existing AI provider resolver (spec 063), show them in an editable modal, and on Save All insert N verified_qa rows that share the same `validated_answer`, `rating_id`, `validated_by`, `validated_at`, `manual_ids`, and `source_chunks` — each with its own `question_text` and independently computed 768-dim embedding (via the existing `ollama_embedder`, unchanged). Provides both a per-approval flow (Review tab) and a per-entry retro-expansion flow (Verified tab, one-at-a-time through the same modal). Graceful degradation when all providers fail: modal opens with the original question only.

No new Python dependencies, no schema changes, no new embedding model.

## Technical Context

**Language/Version**: Python 3.10 (backend), Dart 3.x / Flutter 3.x (frontend)
**Primary Dependencies**: FastAPI, Supabase Python client, httpx (backend, existing); `services.ai_providers.resolver` (spec 063, existing); `services.ollama_embedder` (existing); `services.validated_qa_service` (existing). Flutter Material, `http`, shared widgets from `frontend/lib/widgets/bottom_sheet_widgets.dart` (existing).
**Storage**: Supabase (PostgreSQL + pgvector). Existing `validated_qa`, `answer_ratings` tables. No migrations. `rating_id` is already nullable (migration `20260415000000`) and has **no unique constraint** — multiple `validated_qa` rows can share the same `rating_id`, which is exactly the shared-rating design this spec needs.
**Testing**: pytest (backend), flutter test (frontend) — unit on paraphrase parser + provider-failure path; integration on the Approve-with-variants endpoint.
**Target Platform**: Linux server (FastAPI behind Nginx), Flutter Web PWA.
**Project Type**: Web application (backend + frontend).
**Performance Goals**: Modal opens within 3 s p95 under normal provider conditions (SC-001). Typical Mistral/Gemini latency 1–2 s; embedding N variants at save time adds ~200 ms × N via local Ollama.
**Constraints**: INV-1..INV-5 (see below). Read path (`check_validated_match`) untouched. No similarity threshold changes. No multi-language paraphrasing. English-only v1.
**Scale/Scope**: ~16 existing verified entries for retro-expansion; low ongoing admin-approval volume (a few per week). Cloud-provider paraphrase cost is negligible at this rate.

### Invariants (must hold in all code paths)

- **INV-1**: Every inserted variant row has its own unique `question_embedding` vector of dim 768 (generated by existing `ollama_embedder.embed_single`, model `nomic-embed-text`). Embedding model does NOT change just because the generator provider changed.
- **INV-2**: All variants from one Save All point to the same `validated_answer` text (no divergence across rows in a single approval session).
- **INV-3**: If all providers fail to produce variants, the modal still opens with only the original question. Approval is never hard-blocked by provider failure.
- **INV-4**: `validated_qa_service.check_validated_match()` is not modified. The read/fast-path remains spec 067's responsibility.
- **INV-5**: Existing single-click Approve behavior (one row inserted) is preserved as the fallback whenever the provider chain returns zero variants or when the admin deletes all generated chips and saves only the original.

### Explicitly Out of Scope

- Adjusting similarity thresholds in `validated_qa_service.py` (0.10 direct / 0.25 context stay as-is).
- Multi-language paraphrasing (Arabic & mixed-language are future specs).
- Per-variant thumbs rating UI/schema (all variants share one `rating_id`).
- Any migration or schema change to `validated_qa` or `answer_ratings`.
- A "retroactive auto-approve" bulk button that skips the modal — admin MUST review each entry's variants.
