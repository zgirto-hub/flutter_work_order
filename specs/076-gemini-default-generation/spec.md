# Feature Specification: Default Q&A Generation to Gemini Flash

**Feature Branch**: `076-gemini-default-generation`  
**Created**: 2026-04-16  
**Status**: Draft  
**Input**: User description: "Change the default AI provider from Local (Ollama) to Gemini Flash for the Ask-the-AI Q&A generation step only. Keep all other pipeline stages (query rewrite, HyDE, embedding, reranking) on local Ollama. The provider resolver (spec 063) already supports Gemini with automatic fallback to Ollama on failure. This just changes the default setting from 'local' to 'gemini' and ensures the pipeline stages that should stay local are hardcoded to Ollama rather than routing through the active provider."

## Clarifications

### Session 2026-04-16

- Q: When this spec ships, what happens to existing deployments whose `app_settings` row already holds `active_provider="local"`? → A: One-time migration on first startup — if the stored value is exactly `"local"`, rewrite to `"gemini"`. Admins who had intentionally chosen local must re-select it.
- Q: Does this spec need to impose per-request or per-document restrictions on what content can be sent to Gemini (privacy/data-classification gating)? → A: No. The organization's decision to integrate Gemini in spec 063 is sufficient authorization. This spec operationalizes that decision as the default and does not introduce new content-eligibility rules.
- Q: How should the system handle a 429 / quota-exceeded response from Gemini? → A: Treat 429 exactly like any other failure — immediate per-request fallback to Ollama, one audit row per event, no circuit-breaker state. A dedicated circuit-breaker can be added in a follow-up spec if quota exhaustion becomes a production problem.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Higher Quality AI Answers by Default (Priority: P1)

When a user asks a question in the Ask-the-AI assistant, the system generates the final answer using Gemini Flash instead of the local Ollama model. The user receives a more coherent, detailed, and accurate response because Gemini Flash is a more capable generation model. All other pipeline stages (query rewrite, hypothetical answer generation, embedding, reranking) continue running on local Ollama since they perform well locally and do not benefit from an external model.

**Why this priority**: This is the core value — users get better answers immediately with no workflow changes on their end.

**Independent Test**: Send a question through Ask-the-AI and verify the response is generated by Gemini Flash (visible in latency breakdown or server logs) while rewrite, HyDE, and embedding stages still use Ollama.

**Acceptance Scenarios**:

1. **Given** a user sends a question in the AI assistant, **When** the system processes the query, **Then** the final answer is generated by Gemini Flash and the response quality reflects the stronger model.
2. **Given** the active provider setting has never been manually changed, **When** a fresh deployment starts, **Then** the default provider is Gemini Flash (not local Ollama).
3. **Given** the system is generating an answer via Gemini Flash, **When** the query rewrite, HyDE, and embedding stages execute, **Then** those stages still use local Ollama regardless of the active provider setting.

---

### User Story 2 - Automatic Fallback to Ollama on Gemini Failure (Priority: P1)

If Gemini Flash is unavailable (network issue, API key missing, rate limit, timeout), the system automatically falls back to local Ollama for the generation step. The user still receives an answer — just from the local model — and the fallback event is logged for admin visibility.

**Why this priority**: Reliability is critical. Switching the default to an external provider must not reduce availability.

**Independent Test**: Simulate a Gemini failure (remove API key or block the endpoint) and verify the system falls back to Ollama, returns a valid answer, and logs the fallback event.

**Acceptance Scenarios**:

1. **Given** Gemini Flash is unreachable, **When** a user asks a question, **Then** the system falls back to local Ollama for generation and the user receives an answer.
2. **Given** a fallback occurs, **When** the response is returned, **Then** the system logs exactly one activity row with the fallback details (existing fallback audit contract).

---

### User Story 3 - Admin Can Override Provider (Priority: P2)

An administrator can still change the active AI provider through the existing admin settings. If an admin switches the provider back to "local" or to another supported provider, the generation step respects that choice. The pipeline stages that must remain local (rewrite, HyDE, embedding) are unaffected by admin provider changes.

**Why this priority**: Preserves admin control. The default changes but the override mechanism remains intact.

**Independent Test**: Use the admin provider settings to switch between providers and verify only the generation step changes while other stages remain on Ollama.

**Acceptance Scenarios**:

1. **Given** an admin sets the provider to "local", **When** a user asks a question, **Then** the generation step uses local Ollama.
2. **Given** an admin sets the provider to "gemini", **When** a user asks a question, **Then** the generation step uses Gemini Flash.
3. **Given** an admin changes the provider to any value, **When** the query rewrite or HyDE stages run, **Then** those stages still use local Ollama.

---

### Edge Cases

- What happens when the Gemini API key is not configured at all? The system falls back to Ollama gracefully on every request until a key is provided.
- What happens during a provider switch mid-request? The resolver caches the provider for 60 seconds, so in-flight requests use the provider resolved at the start of the request.
- What happens if the Ollama server is also down? Both generation and local pipeline stages fail; the system returns an appropriate error to the user (existing behavior, no change needed).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST use Gemini Flash as the default AI provider for the Q&A answer generation step when no admin override has been configured.
- **FR-002**: System MUST keep query rewrite, HyDE generation, history compression, and embedding stages hardcoded to local Ollama, regardless of the active provider setting.
- **FR-003**: System MUST change the default provider constant from "local" to "gemini" so that new deployments and fresh databases default to Gemini Flash.
- **FR-004**: System MUST preserve the existing automatic fallback mechanism — if Gemini Flash fails (timeout, error, empty response, missing credentials, rate-limit / quota-exceeded response such as HTTP 429), the generation step falls back to local Ollama. Rate-limit and quota-exhaustion responses MUST be treated identically to any other failure — no special circuit-breaker state, one audit row per fallback event.
- **FR-005**: System MUST preserve the existing fallback audit logging contract (one activity row per fallback event).
- **FR-006**: System MUST allow administrators to override the default provider through the existing admin provider settings interface.
- **FR-007**: Pipeline stages that call local Ollama directly (rewrite, HyDE, embedding) MUST NOT be routed through the provider resolver, ensuring they are immune to provider changes.
- **FR-008**: System MUST perform a one-time migration on the first startup after this feature is deployed: if the stored `active_provider` value in `app_settings` is exactly `"local"`, rewrite it to `"gemini"`. The migration MUST run at most once per deployment (idempotent on subsequent starts) and MUST log a single audit event recording that the migration occurred, the previous value, and the new value. Administrators who had intentionally selected `"local"` before this deploy must re-select it via the admin UI after the migration — this is an accepted trade-off to deliver the immediate-value promise of User Story 1.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: After deployment, all Q&A generation requests use Gemini Flash by default (verifiable via server logs showing the active provider).
- **SC-002**: Query rewrite, HyDE, and embedding stages continue using local processing with no change in their response times (within 10% of baseline).
- **SC-003**: When the external generation provider is unavailable, 100% of requests still return an answer via the fallback mechanism.
- **SC-004**: Admin provider override continues to work — switching to any supported provider changes only the generation step.

## Assumptions

- The Gemini API key environment variable is already configured on the production server.
- The existing provider resolver, fallback mechanism, and audit logging (specs 063, 065) are stable and do not require modification — only the default value changes.
- Query rewrite, HyDE, and embedding stages already call Ollama directly (not through the resolver), so they are naturally isolated from provider changes. This spec confirms and documents that isolation as intentional.
- The provider settings row in the database may or may not exist on a given deployment. When absent, the system uses the hardcoded default — this spec changes that default from `"local"` to `"gemini"`. When the row IS present with the literal value `"local"`, the one-time migration in FR-008 rewrites it to `"gemini"` on first startup post-deploy. All other stored values (e.g., `"gemini"`, a different provider key, or a custom admin choice made after this spec ships) are left untouched.
- No frontend changes are required — the provider switch is entirely backend and transparent to end users.
- Data governance is out of scope for this spec: user queries, retrieved chunks (product manuals, validated Q&A), and any prompt context sent to Gemini flow through Google's API without per-request or per-document eligibility filtering. The organization's decision to integrate Gemini (spec 063) is treated as sufficient authorization at the global level. Any future per-content sensitivity classification or user-level opt-out would be addressed in a separate spec.
